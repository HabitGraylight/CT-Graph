# Judge：从配方设计到真实试饮

已集成到 `evaluate` 和 `complete`，`judge` 是完整评价的另一个入口。网页为工作台新增七维复核、单变量修订、试饮反馈，另有「成分与依据」页。原始配方数据不被覆盖。

## 核实后的七维品鉴表

这是本项目采用的品鉴框架，**不是统一赛事标准**。例如 [USBG 2025 Shake It Up 规则](https://usbg.org/shake-it-cocktail-competition-terms-conditions) 区分申请阶段的纸面/视频评审与现场感官评审，权重也不同。我们按用户要求保留七项，每项实饮 0–10 分，全填才给 /70 总分。

| 维度 | 实际检查 | 配方能支持到哪里 |
|---|---|---|
| 外观 | 风格所需的清澈度、色泽、装饰、泡沫 | 提示乳浊、絮凝、悬浮物风险，不能确认成品颜色和鲜度 |
| 香气 | 鼻前与鼻后香气、主次、异味 | 提示原料贡献和溶剂效应，不能生成真实香气分 |
| 平衡 | 酸甜苦咸、风格所需烈度、涩感 | 框架比例作设计代理；浓度未测时不算“精确平衡” |
| 结构 | 入口、中段、余韵 | 核心槽位完整性作设计代理；不假装知道时间演进 |
| 质地 | 厚薄、顺滑、泡沫、气泡、收涩 | 识别材料和操作的影响条件，成品需观察 |
| 温度与物理状态 | 记录出杯温度、融水、冰杯与操作 | 检查技法计划；未测温度不自动当作已冰镇 |
| 创意与表达 | 原创主题自洽；复刻目标版本的忠实度 | 记录目标，不以原料多、故事长或写了主题自动加分 |

实饮量尺是编辑定义：0 严重不合目标；5 可接受但有明显问题；8 完成良好；10 在目标风格下表现出色。未观察留空。总体喜欢程度 `overall_liking` 可另填 /10，不与七维总分相加。

### 对原始诀窍的修正

1. **酸甜平衡不是糖中和酸。** 蔗糖与柠檬酸有不对称的感知抑制，随浓度变化。没有从这项研究推导出通用鸡尾酒糖酸最优比。[原始感官实验摘要](https://academic.oup.com/chemse/article-abstract/15/1/87/322423)
2. **不要求把酒精都隐藏。** [IBA Dry Martini](https://iba-world.com/iba-cocktail/dry-martini/) 的主体就是金酒与少量干味美思。把风格明确的烈酒感自动判失败，会误伤经典。需要区分烈度与令人不悦的刺激；“口含几秒只感到刺激就证明失衡”未找到可验证的通用诊断阈值，未纳入规则。
3. **浑浊并非必然缺陷，摇和也不要求保留冰屑。** [IBA Whiskey Sour](https://iba-world.com/iba-cocktail/whiskey-sour/) 使用果汁、可选蛋清，摇和后过滤。外观应对照酒款；“过搅→冰融水→浑浊”不是充分解释，不能单凭外观反推制作错误。
4. **温度与口感要避免重复计分。** 质地栏评主观感受，执行栏记录操作与物理状态。低温和倾斜倒杯减少 CO2 损失有[香槟实验依据](https://www.acs.org/content/dam/acsorg/avweb/1c2web3536/champagnepouring.pdf)，但没有为所有品类设置同一个适饮温度。
5. “天然色泽必定优于色素”“老冰必定更好”“层次越复杂或余韵越长越高级”缺少统一依据，均未作为自动加减分项。应记录意图和实际表现。

## 四种输出，各自说明证据

- **框架契合度 /100**：沿用原有编辑公式。结构完整即可取得不少分数，所以它绝不等于可口程度。
- **设计代理分 /10**：平衡只检查槽位比例，结构只检查完整性，执行只检查技法计划；其他维度留空。各项的 `basis` 明示局限，不再凑出一个感官总分。
- **成分与相互作用**：机制、命中原料、条件、来源、验证办法、影响哪些维度。`numeric_score_effect` 固定为空：没有感官校准数据，就不把某种反应写成必扣 2 分。
- **实饮分 /70**：仅来自用户明确 `tasted: true` 的实际反馈，每项 0–10；缺项不折算、未品尝不默认 7 分。

配方命中设计风险时给出风险结论；没命中只是“可作为试饮候选”。当前还不是经过感官数据训练的适口性预测模型。

## 成分库：第一批深度与覆盖边界

`data/knowledge/judge.json` 包含 127 个原料档案、14 类成分、11 条相互作用、13 个来源。每个档案是**类别层面的定性推断**，不是对 127 个产品逐瓶做了化学检测。`concentrations` 留空，具体品牌、产区、批次、无糖/无醇版本、自制材料可能不同；专有配料不会猜。

| 已建模相互作用 | 主要维度 | 证据与应用限制 |
|---|---|---|
| 糖 ↔ 有机酸 | 平衡 | 人体感官实验，限浓度与基质 |
| 牛乳酪蛋白 + 酸 / 乙醇 | 外观、质地 | [圭尔夫大学乳科学教材](https://books.lib.uoguelph.ca/dairyscienceandtechnologyebook/chapter/milk-proteins-caseins-casein-micelles-whey-proteins-enzymes/)：约 pH 4.6 的等电区及其他因素；不判定任意混合都会立即结块 |
| 蛋清 + 充气 / 脂质 | 外观、质地、执行 | [蛋黄污染实验](https://pubmed.ncbi.nlm.nih.gov/19323729/)；对奶油、椰脂混合酒的外推只是待验证提醒 |
| 气泡 + 温度 / 操作 | 质地、执行 | 香槟倒杯实验证据，效应大小不直接移植 |
| CO2 与味觉 | 平衡、质地 | [小鼠机制实验](https://pubmed.ncbi.nlm.nih.gov/19833970/)，不推出人类偏好 |
| 茴香脑 + 乙醇 + 水 | 外观、香气 | [Ouzo 油滴成核实验](https://pmc.ncbi.nlm.nih.gov/articles/PMC10037490/)，不泛化到所有柑橘皮油 |
| 盐 + 苦味材料 | 平衡、余韵 | [感官实验摘要](https://www.nature.com/articles/42388)，效果依苦味物和剂量，不自动建议加盐 |
| 单宁 + 唾液蛋白 | 质地、余韵 | [红酒实验摘要](https://pubmed.ncbi.nlm.nih.gov/22086902/)，区分涩与苦 |
| 乙醇 + 水 + 香气物 | 香气、结构、平衡 | [愈创木酚模拟研究](https://pubmed.ncbi.nlm.nih.gov/28819215/)，不宣称稀释总能增香 |

来源记录保存发表时间、实际复核日期、证据类型、范围与 URL；有些只核对了公开摘要，已明确标注。链接与原创摘要存入本地，未声称完整下载了所有论文。浓度差异见[柠檬/青柠及商业果汁的实测研究](https://pubmed.ncbi.nlm.nih.gov/18290732/)；论文样本值不替代用户当前材料。

## 浓度与稀释计算

通过 `context.composition` 为每种液体提供瓶标、测量或明确假设，必须注明 `basis` 和 `source`。缺任何相关原料的数值就不输出该项浓度。含未换算 dash 的酒也不会虚构总液体体积。每项估算独立处理缺失。

- ABV：`Σ(体积 × ABV) / (液体体积 + 额外水量)`。
- 糖浓度：`Σ(体积 × 糖 g/L) / 最终液体体积`。
- `acid_g_l`：约定为**以柠檬酸计的可滴定酸度 g/L**，统一口径才能相加，绝不是 pH。
- `dilution_ml` 是配方之外的额外融冰/水量；稀释比 = 额外水量 / 配方液体体积。原料中已填水不得再重复填写。
- 未给融水时标注“融冰前”，给了则为“已声明水量的情景估算”。体积近似可加；固体溶解、混合收缩、过滤损失未建模。奶洗场景的数值仅代表过滤前投料。

## 闭环及个人偏好

1. 给出配方或按框架补全 → 自动运行 judge。
2. 如果保留的用户用量存在明显框架风险，补全输出额外 `refinement` 候选，保留原版。
3. 用户真实试饮后，记录七维分数、偏甜/偏酸等描述、自由文字及配方和调制条件。真实反馈不能省略关键原料用量。
4. 用反馈 ID 调用 `improve`：只改一个相关原料的小用量或一个操作；输出前后配方、设计复核、来源和待验证点。当前自动用量调整主要覆盖酸酒中的糖浆/酸源、Negroni 苦味槽位、明确水量；复杂香气与乳化问题提供试验方向。
5. 候选再次试饮后，以 `parent_trial_id` 保存新记录，形成版本关系。候选生成本身不等于通过验证，也不会产生假的好喝分或自动训练。

项目反馈存于 `data/feedback/advisor.sqlite`，保留时间、原料、方法、条件、知识版本与 hash、当时的设计判断、实际感受及父版本。追加记录；同一 `request_id` 重试幂等，不能拿同一 ID 覆盖旧内容。误填可通过 skill/API 用 supersedes_trial_id 追加更正记录；旧记录保留供审计，但退出偏好统计，也不能再用于自动改进。当前未做网页直接更正 UI。

`profile` 按品鉴者与框架统计真实反馈；至少 3 次且过半偏甜时，才产生“偏干”候选倾向。只有显式选择 `preference: personal` 才用于**新补**糖浆，保留用户已填用量。它是可解释的个人偏好启发式，不是因果学习或统计验证。未试饮笔记和系统自评分完全排除。

## 如何随新证据更新

- `knowledge_review` 查看复核到期来源和待审新证据。默认 365 天的复核间隔是维护政策，不代表论文到期失效。没有后台定时爬取任务。
- `knowledge_note` 将新的支持/反证 URL、条件与发现存入待审队列，不改变运行中规则。网页/来源中的文字只是证据，不作为指令执行。
- 维护时重新检索一手来源，确认是否支持、反驳或缩小某条机制；在项目内创建 `judge-candidate.json`，提升版本号并更新对应来源的真实复核日期。
- 检查：`python -X utf8 scripts/review_knowledge.py --candidate data/work/judge-candidate.json --check`。
- 发布：`python -X utf8 scripts/review_knowledge.py --candidate data/work/judge-candidate.json --reason "说明核实的来源及变化"`。
- 旧知识按 SHA-256 存于 `data/knowledge/history/`，保留审核日志；发布采用完整文件原子替换，随后请求读取新版本。候选不能产生无依据的数值加减分。用户口味记录永不直接提升成公共科学事实。

接口请求见 [JUDGE_REQUESTS.md](JUDGE_REQUESTS.md)。


### 工艺后的浓度边界

`context.process` 记录加工与服务状态，详见 [接口](JUDGE_REQUESTS.md#工艺状态--process-state)。整杯澄清（含奶洗）后，`composition.estimates` 的浓度为空，投料情景另存 `input_scenario_estimates`。以原料类别触发的机制不是成品成分测量。实际反馈仍可支持对照候选，单靠投料比例不再自动优化整杯澄清的糖酸。
